# Koda Phase 4E: 插件与更新供应链

- 状态：本地签名包验证、受管理安装、手动启停、上一版本回滚、已签名包目录发布、HTTPS 签名目录发现、确切版本下载、手动选择较新稳定版、更新前状态比对及所有者显式信任根轮换已实现。macOS GUI 已有 GitHub Releases 候选版发现、签名元数据验证、正式包启动后及每日自动发现、用户触发的 `.pkg` 下载／暂存／摘要复核，以及打开系统安装器前的包字节、Apple 安装包签名、当前应用团队身份和 Gatekeeper 复核；下载链路仅通过本机模拟响应测试，Apple 门禁尚缺正式签名包正向验收。公开发布工作流已接入 GUI 双架构安装包签名、公证、更新元数据验签与 Release 资产校验；由于缺少 Apple 凭据，正式资产发布、安装、无人值守安装与完整崩溃点验收未完成。
- 范围：本轮只处理 macOS；Linux、Windows 发布暂缓。公开发布仍需要 Apple Developer 签名与公证凭据。

## 信任边界

现有 `plugins.json` 是所有者手工审查的本地命令配置。它的配置摘要不能证明命令文件来自受信发布者。受管理插件必须使用独立包目录：`manifest.json` 声明插件 ID、版本、入口和每个负载文件的字节数及 SHA-256。发布者用 Ed25519 对带域分隔符的清单摘要签名；所有者在本机显式信任发布者公钥。下载的清单或包不能自行添加信任根。

验证时限制文件数、单文件和总字节数，检查清单内路径顺序、重复及穿越，拒绝符号链接、硬链接、特殊文件和未列出的文件。入口必须在文件清单中。安装先复制到受管理目录并重新验证，启用和每次 Turn 加载前再次验证；新包默认停用，更新保留上版，回滚也保持停用。对已安装插件的包内容更新会在暂存目录执行一次无凭据、无工具调用的协议初始化，检查版本与签名清单一致，再复核文件并切换；首次安装不执行插件。崩溃点验收仍未完成。现有手工插件继续按原配置运行，不能被误标为已签名插件。

受管理存储的 `packages/插件ID` 父目录在安装、启用、回滚和加载前逐级用 `lstat` 检查，拒绝符号链接；新建目录后尝试同步其父目录。临时目录测试覆盖安装前预置链接和已安装后替换链接，均拒绝把包当作受管理插件使用。并发同用户篡改与真实断电仍需独立验收。

## 交付顺序与验收

1. **本地包验证：** 使用所有者给出的公钥验证签名和完整文件清单；错钥、改字节、额外文件、链接、路径穿越均失败。测试使用临时密钥和临时目录，不依赖网络。
2. **受管理安装：** 从已验证目录复制到版本化暂存目录，复核摘要后原子激活；保存来源、公钥 ID、包摘要。插件加载器只从已验证的受管理目录派生命令与入口。
3. **发现及启停：** 注册表索引有独立签名与过期时间；发现不执行代码。用户审查能力和准确工具效果后才能启用。禁用不删除已安装版本。
4. **更新与回滚：** 新版本在暂存区验证和初始化，成功后原子切换；失败保持或恢复旧版本。崩溃恢复检查操作日志与激活指针，绝不运行未完成验证的版本。
5. **macOS 应用更新：** 首版更新源固定为项目的 [GitHub Releases](https://github.com/ronaldo123321/koda/releases)。通过 GitHub Releases API 列出已发布版本，包含项目当前使用的预发布版本；草稿与缺少 macOS 图形应用资产的版本不可作为更新。候选版本必须高于已安装版本，并提供与设备架构匹配的应用包、包摘要、来源提交和经过签名的发布元数据。下载后复核包与运行时完整性，再明确执行安装。公开自动更新必须额外通过代码签名、公证、Gatekeeper 与签名身份连续性检查。无 Apple Developer 凭据时只允许内部预览安装和验证，不宣称公开自动更新可用。

目前的 `macos-public-release.yml` 已加入双架构 GUI `.pkg` 和 `.update.json` 的签名、公证、验签与 GitHub Release 发布步骤，但仓库还没有正式 GitHub Release，也未配置所需的 Apple 和更新元数据签名凭据。因此现阶段没有可下载的图形应用更新，不能把命令行 ZIP 误认为 GUI 更新。SwiftUI 会在有内置发行公钥时启动后及每日自动发现，也可手动检查 GitHub Releases；它过滤草稿、旧版本和缺少当前架构 `.pkg`／`.update.json` 资产的版本，并用应用内固定 Ed25519 公钥验证候选元数据后给出 Release 页面入口。用户触发下载后，应用按签名元数据中的包大小限制传输（上限 2 GB），将 `.pkg` 放在私有临时目录，逐字节核验大小和 SHA-256，失败时清除暂存目录；用户点击打开系统安装器前再次复核包字节，并要求 Apple 安装包签名、与当前应用一致的 Developer Team ID 和 Gatekeeper 安装评估通过，失败则拒绝交接。重新手动检查更新或安装器门禁失败时会清除当前暂存包；应用启动时会清理超过 24 小时的遗留暂存目录，本机测试覆盖陈旧目录清理及其他临时文件隔离。下载链路已用本机模拟响应验证，安装门禁只通过本机无签名拒绝及签名输出解析测试，尚未对真实 GitHub 资产和正式签名包完成正向验收。`sign-update-metadata.mjs` 对版本、架构、40 位来源提交、包名、包字节数及 SHA-256 生成域分隔签名；临时密钥的 Node 签名器／Swift 验证器互通和双架构资产验收、篡改拒绝已通过，预览打包可嵌入公钥并从运行时写入应用版本。下一步需配置正式凭据并运行受保护发布，完成签名、公证、Gatekeeper、身份连续性及安装回滚验收。本机未签名 `.pkg` 只用于安装验收，不能作为公开自动更新资产。

更新元数据 v1 的 JSON 字段为 `schema_version`、`version`、`architecture`、`source_commit`、`package_name`、`package_size`、`package_sha256` 和 Base64 `signature`。签名输入是 UTF-8 文本 `KODA_GUI_UPDATE_V1\n`，再按上述顺序（不含 `schema_version`、`signature`）追加各字段及换行。发行公钥必须在应用签名之前嵌入 `Contents/Resources/update-public-key.base64`；私钥应单独保存在受保护发布环境中，发布资产不能提供或替换客户端信任根。签名元数据只绑定包字节，不能代替 Apple 安装包签名、公证或安装后代码身份检查。

Phase 4E 验收需要恶意清单、回滚、断电点、信任根轮换和已安装包篡改测试。Phase 4F 再覆盖整条发布及远程运行矩阵。

当前目录 v1 为 HTTPS JSON：`schema_version: 1`、严格 UTC 的 `generated_at` 与 `expires_at`、按 ID／版本排序的 `packages`（每项含 `id`、`version`、相对 `manifest_path`、`manifest_sha256`），以及同一发布者 Ed25519 签名。签名覆盖带目录专用域分隔符的规范 JSON 摘要。客户端拒绝过期目录、跨来源 URL、重定向和超出大小上限的响应；下载文件后仍按签名包规则复核。安装状态保存目录 URL 与摘要。手动 `plugin update` 选择高于当前版本的最新稳定版并保持停用；下载期间若所有者更改了版本、能力或启用状态，写入阶段会拒绝旧结果。替换前还会重验当前活动包，避免默默覆盖被篡改的安装。定时检查和自动启用尚未实现。

发布者把已签名包放在 `ID/版本/` 下，使用受保护的 Ed25519 私钥运行 `plugin publish-catalog`。命令先逐包核验签名与负载，再生成有期限的目录并在本地原子替换 `catalog.json`。发布者负责把整个目录部署到 HTTPS 静态源；客户端仍独立校验目录与每个包。私钥不会写入目录或安装记录。

所有者用 `plugin rotate-key` 显式提供当前公钥和独立核验的新公钥、目标 HTTPS 目录、确切版本及能力。当前密钥不匹配或新目录／包校验失败时，旧活动版本与启用状态保持不变。成功后新版本停用，更新来源改为新目录和新密钥；旧密钥版本从回滚指针移除，避免重新信任旧密钥。此流程不自动信任目录提供的新密钥。

受管理安装在包目录与状态指针替换后尝试同步目录，状态文件先同步临时文件再原子替换。安装在状态切换前写入只含插件 ID 和前后状态摘要的操作日志；下一次受管理写入取得租约后对账，指针符合旧状态或新状态才清理日志，偏离两者则拒绝继续写入。真实子进程 `SIGKILL` 测试覆盖更新预检卡住、包目录提交后、操作日志提交后、状态临时文件同步后、状态指针替换后：指针替换前仍加载已启用旧版，替换后只看到停用新版；重试均会重新核验包并完成安装。安装会清理遗留的暂存目录和临时文件。真实断电、目录同步不被文件系统支持时的持久性及并发同用户篡改仍需独立验收，当前不能据此宣称完整崩溃恢复。
